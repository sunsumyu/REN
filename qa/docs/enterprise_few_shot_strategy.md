# 🏥 企业级医疗 Think CoT 微调数据：Few-Shot 架构优化方案

针对高质量医疗大模型（类似 DeepSeek-R1, o1 风格）的推理（CoT）微调数据生成，纯依靠 Zero-Shot 与长串 `<rule>` 极易导致模型产生“注水废话”与“工程词汇泄漏”。

本方案采用 **“对比型动态少样本”（Contrastive Dynamic Few-Shot）** 策略，旨在从源头拔高“问题”的思维熵，并净化“答案”的推演路径。

---

## 一、 核心设计哲学
1. **Show, Don't Tell（展示胜于说教）**：用“烂问题/好问题”的鲜明对比，直接阻断模型的偷懒本能。
2. **去系统化（De-systemization）**：在 `<think>` 示例中，绝对屏蔽 `JSON`, `Refs`, `System Prompt` 等工程词汇，强制模型将内心独白锁定在**纯粹的病理/药理分析**。
3. **多维摩擦（Multi-dimensional Friction）**：给定的示例必须包含知识冲突或边界权衡（如：获益与毒性的博弈），强制产生“反事实推理”。

---

## 二、 问题生成端 (Question Creator) Few-Shot 设计

问题生成的 Few-Shot 必须采用 **【反面教材 🆚 正面教材】** 的对比模式。通过这种对比，指导模型如何将一个低维的“说明书查表题”升维成“高价值临床推理题”。

### 💉 示例设计方案（可注入 Prompt 中）

> [!TIP]
> **注入方式**：在 `QUESTION_CREATOR_TEMPLATE` 中增加 `<few_shot_examples>` 模块，让模型在生成问题前先学习“升维逻辑”。

```markdown
<few_shot_examples>
【场景：给定知识点“丙戊酸钠儿童起始剂量为400mg/日”】

🔴 [⛔ 严禁模仿/Rejected] 负面示例 (纯事实检索):
"体重超过20kg的儿童使用丙戊酸钠口服液的起始剂量是多少？"
(错误原因：只需查表，零思维熵，无法激发模型的思考。)

🟢 [🌟 必须遵循/Chosen] 黄金示例 (临床多维权衡):
"一名6岁男童（22kg）新确诊失神发作，既往有轻度肝功能异常（ALT升高）。若计划启动丙戊酸钠治疗，在决定起始剂量时应如何结合其生理学特点与该药物的黑框警告进行综合评估？"
(优秀原因：将干瘪的剂量数据，融入了“体重计算”+“儿童肝酶代谢特点”+“药物肝毒性”的三重摩擦，极具 CoT 推理价值。)

---

【场景：给定知识点“替吉奥严重肝损伤禁用”】

🔴 [⛔ 严禁模仿/Rejected] 负面示例 (简单分类):
"替吉奥对哪类肝功能异常的患者禁用？"

🟢 [🌟 必须遵循/Chosen] 黄金示例 (边界探究与机制倒推):
"为什么说明书将替吉奥的绝对禁忌严苛限定在'重度肝功能异常'？这种限制与该药物的前体转化和代谢产物清除机制有何深层关联？"
</few_shot_examples>
```

## 三、 答案生成端 (Answer Generator) Few-Shot 设计

这是决定模型 `<think>` 质量的核心环节。Few-Shot 的 `<think>` 必须是一个**纯净的、具有假说验证和机制倒推的医生内心独白**。

### 🩺 示例设计方案

> [!IMPORTANT]
> **严格红线**：示例的 `<think>` 中**严禁**出现“根据提供的文档”、“我们被要求输出格式”、“拆解子问题”等元叙述。

```markdown
<few_shot_examples>
【输入问题】：为什么阿司匹林在哮喘患者中可能诱发致命的支气管痉挛（阿司匹林哮喘）？

【期待的结构化输出】：
<think>
这是一个经典的药物不良反应机制问题，不能仅停留在“过敏”的表象。
首先回溯阿司匹林的药理靶点：它非选择性抑制环氧合酶（COX-1 和 COX-2）。
这会带来什么级联反应？花生四烯酸的代谢途径有两条：环氧合酶途径和脂加氧酶途径。当 COX 途径被阻断后，原本该走这条路的底物就会发生“交通改道（Shunting）”，大量涌向脂加氧酶途径。
脂加氧酶途径的产物是什么？是白三烯（Leukotrienes）。白三烯是极其强烈的支气管平滑肌收缩剂和促炎介质。
反向验证：临床上使用白三烯受体拮抗剂（如孟鲁司特）能否缓解？可以，这印证了上述病理生理学推演。
因此，阿司匹林诱发哮喘的本质并非传统的 IgE 介导的免疫过敏，而是酶学代谢途径的强行偏移导致了药理学上的“毒性产物蓄积”。
</think>

}
</few_shot_examples>
```

## 四、 关键考量：Token 消耗与反向提示陷阱 (Negative Prompting Trap)

在实施 Few-Shot 时，常见的两个顾虑及解决方案如下：

### 1. Token 消耗评估
- **成本与收益**：输入端 (Input Tokens) 确实会增加（约 200-400 Tokens），但由于大模型生成（Output）的成本通常是输入的数倍，高质量的 Few-Shot 能有效抑制模型在 `<think>` 中生成数百字的“工程系统废话”（如“我正在按 JSON 格式输出...”）。**省下的 Output Token 往往能抵消 Input Token 的增加**。
- **优化策略**：使用支持 Prompt Caching 的模型（如 Claude 3.5, DeepSeek-V2），固定的 Few-Shot 段落会被缓存，使输入成本降低 90% 以上。

### 2. 反例（Bad Case）导致模型注意力偏移的风险
在学术界，强调“不要做什么”有时反而会激活大模型的特定输出（即反向提示陷阱）。为规避此风险，本方案采取了以下**对齐压制法则**：
- **强化 RLHF 偏好标记**：在反例前添加醒目的负面标记 `[⛔ 严禁模仿/Rejected]`，在正例前添加 `[🌟 必须遵循/Chosen]`。现代大模型在出厂前对这两个词有极强的对齐敏感度。
- **篇幅压制 (以正克反)**：反例必须极度简短（仅 1-2 句话点出错误），而正例必须极其丰满。这样模型的注意力权重 (Attention Weights) 会自然收敛到结构完整的正例上，避免记忆污染。
