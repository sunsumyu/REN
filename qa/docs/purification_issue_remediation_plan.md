# 医疗问答提纯问题治理方案

本文整理当前提纯流程中已暴露的几类问题及对应治理方案，目标是在不牺牲事实可追溯性的前提下，降低 RAG/工程残留、事实幻觉、过度回滚和漏检风险。

---

## 1. Source 与事实锚点治理（含 RAG Source 脱敏）

### 问题

当前提纯引擎会将 refs 组装为 `Confirmed Clinical & Literature Facts` 后喂给生成模型。虽然系统提示禁止输出 `refs`、`实体库`、`图谱` 等词，但输入中仍可能包含如下结构：

```text
[refs:《实体库:索磷布韦维帕他韦片》] 概念定义: ...
```

这主要由于在 `core/purification_engine.py` 中直接将原始医学文献 `source` 拼接为 `f"- [{src}] {clean_ctx}"` 并注入生成模型。模型在生成中极其容易代偿性残留“实体信息”、“概念定义”、“知识库”、“信源”等软性工程表达。

### 治理原则

不要直接向模型暴露物理数据源的工程名称，将“给模型看的事实”和“系统内部保存的来源”分离，并在模型生成前执行**源头标签脱敏**。

```text
原始 refs
-> 内部保留 source / provenance
-> context 抽取为 fact_xxx 原子事实，并以 [文献_xx] 进行中性标签化
-> 生成模型只看清洗后的自然语言事实与 [文献_xx] 标签
-> Judge / Audit 使用 fact_xxx -> source 映射做追溯和校验
```

### 建议方案

1. 生成模型输入中不出现 `source` 原文。
2. 将 `context` 解析为最小事实单元，例如：

```text
fact_001: 索磷布韦维帕他韦片用于治疗基因1-6型慢性丙型肝炎病毒成人感染患者。
```

3. 系统内部保留映射：

```text
fact_001 -> refs:《实体库:索磷布韦维帕他韦片》
```

4. 输出后由事实一致性校验器判断每个新增医学事实是否能被 `fact_xxx` 支撑。

这样既能保留可追溯性，又能避免 RAG 工程词进入模型语言空间。

## 2. 提示词冲突治理

### 问题

当前提纯提示词同时要求：

- 高熵、深机制、带问号反思的 CoT。
- 严格贴合 refs，禁止事实幻觉和外推。

当原始 refs 稀疏、题目本身简单，或证据只支持直接事实时，这两类目标会相互冲突。模型为了满足“深推理”要求，容易补机制、补人群、补临床意义，随后被 Quality Gate 拦截。

### 治理原则

先判断题目是否值得深推理，再决定生成风格。

### 建议方案

1. 建立证据覆盖度判断：

```text
HIGH_EVIDENCE: refs 含机制、数值、因果链，可允许深推理。
LOW_EVIDENCE: refs 仅含定义、适应症、包装、贮藏、剂量等直接事实，强制极简。
NO_EVIDENCE: refs 无可用事实，只能输出边界性说明或回滚。
```

2. 对简单题强制 `simplify`：

- 适应症覆盖范围
- 贮藏条件
- 包装规格
- 成分构成
- 单项比例/数值
- 简单禁忌或用法

3. 将“问号反思锚点”从硬性门槛改为软性加分项。

4. 明确规定：

```text
如果 fact 包没有机制、靶点、通路或临床试验事实，则禁止生成具体机制推演。
```

5. 对证据不足时允许自然收束：

```text
现有事实只能支持该分类/数值/适应症结论，不能据此推断更具体的机制或人群差异。
```

这样可减少模型为了追求逻辑深度而产生的高仿真幻觉。

## 3. 证据路由治理

### 问题

当前证据路由主要依赖关键词分类。对于 GENERAL_MEDICAL 类型，机制、药理、疗效、主治、适应症、临床试验等内容都可能进入核心或边界证据。

这会导致简单问题被喂入过多旁路信息。例如“某药可用于哪些基因型”本应只需要基因型覆盖事实，但 refs 中的用药方法、肝肾功能、呕吐补服、临床安全性等信息也可能影响模型，使 Think 和 Answer 写宽。

### 治理原则

证据能否进入 prompt，应取决于它是否直接回答当前问题，而不仅是它是否医学相关。

### 建议方案

1. 建立三层路由：

```text
题型层: 识别问题是剂量、适应症、成分、贮藏、机制、不良反应等。
证据角色层: 将 refs 分为 CORE、BOUNDARY、BLOCKED、UNUSED。
支撑层: 判断每条事实是否直接支撑问题答案。
```

### 证据分级建议

CORE:

- 能直接回答问题的事实。
- 必须进入生成 prompt。
- 必须在最终答案中体现。

BOUNDARY:

- 与问题有关，但不是主答案。
- 最多允许一句边界提醒。

BLOCKED:

- 可能诱导模型跑偏或脑补的事实。
- 不进入生成 prompt。

UNUSED:

- 无关、重复、抓取异常、无事实内容。

### 示例

问题：

```text
索磷布韦维帕他韦片可用于治疗哪些基因型的慢性丙型肝炎感染？
```

CORE:

```text
适用于基因1-6型慢性HCV成人感染患者。
适用于所有主要HCV基因型。
```

BOUNDARY:

```text
成人患者适用。
```

BLOCKED:

```text
呕吐后是否补服。
肾功能损害剂量。
头痛、疲劳、恶心等安全性。
利巴韦林联合方案细节。
```

这样能避免答案宽度超过问题宽度。

## 4. 回滚逻辑治理

### 问题

当前管线中，只要某一 planner 提纯失败，或 planner 数量变化，整行就会回滚。对于多视角样本，一个失败视角会连带影响其他已成功视角。

这会导致：

- 成功结果被浪费。
- 历史失败记录膨胀。
- 行号不断漂移。
- 后续审计容易把历史原始行号和当前数据行号混淆。

### 治理原则

将整行事务改为按 planner 的局部事务。

### 建议方案

1. 每个 planner 独立提纯、独立打分、独立验收。
2. 失败 planner 单独进入重试或隔离队列。
3. 成功 planner 可先保留，不被失败 planner 连坐。
4. 只有以下情况触发整行回滚：

- 所有 planner 都失败。
- 核心 planner 失败且无法保留原答案。
- summary 重生成失败。
- Answer 与 Think 出现严重事实不一致。
- 行级 JSON 结构损坏。

5. 审计日志中区分：

```text
line_status: partial_success / success / rollback / quarantined
planner_status: success / failed / quarantined / pruned
```

6. 对失败 planner 保留原始版本或标记为待清洗，而不是直接导致整行物理删除。

这样可以降低误杀率，并减少行号漂移对后续审计的干扰。

## 5. 验证器与残留检测治理

### 问题

当前验证器的禁词表偏窄，主要覆盖：

```text
JSON, Schema, 免责声明, 忽略, refs, 根据参考文档, 图谱关系, 概念定义, 知识关联
```

但实际残留中还有大量软工程表达：

```text
知识库
信源
实体信息
现有素材
查询确证记录
在线数据抓取
网络抓取异常
数据源
条目
收录
最终一个逻辑闭环形成
```

另外，验证器主要扫描 think，容易漏掉 answer_body 中的工程残留。

### 治理原则

1. **本地验证极简化**：本地验证层（Validator）必须保持轻量、高效，以**极低的延迟**阻断显式工程残留。避免在该层增加额外的轻量大模型分类器，防止产生额外的推理延时与成本。
2. **多文本同步扫描**：必须同时覆盖 `think_content`、`answer_body` 与 `summary`，不能仅局限于 `think` 字段。
3. **复杂检测向 Judge LLM 旁路分流**：涉及上下文语义理解的“元叙述/做题家叙述”或复杂的软性工程泄露，不应在本地用规则硬核拦截（容易误杀或漏判），而应融入后续已在运行的 Judge LLM 的 Purity Rubric 中，进行语义级检测。

### 建议方案

1. **扩展禁词黑名单（规则与 Trie/AC 过滤）**：
   在本地 Validator 维护一个扩展禁词表，并使用高效的多模式匹配算法（如 Aho-Corasick 算法或前缀树 Trie-Tree）实现对多字段的扫描，匹配成功即触发重写或人工标记。

   - **工程容器词**：`refs`, `RAG`, `schema`, `JSON`, `source`, `context`, `metadata`
   - **知识库/图谱来源词**：`实体库`, `图谱关系`, `知识图谱`, `关系库`, `数据库`, `知识库`, `数据源`
   - **检索过程词**：`检索到`, `抓取`, `收录`, `条目`, `在线公开检索`, `未收录`, `网络异常`, `参考资料有限`
   - **软性来源残留**：`信源`, `素材`, `确证记录`, `概念定义`, `实体信息`, `知识关联`

2. **建立“泄露词候选池”自进化机制**：
   - 提取失败审计日志与标注反馈中的新残留词汇，录入黑名单候选池，经审查确认后定期同步到本地过滤器的匹配库中。

3. **旁路化复杂语义检测（分流至 Judge LLM）**：
   - 本地 Validator **不运行任何 LLM 进行语义分类**。
   - 将“是否以报告腔/做题家视角切入”、“最终一个逻辑闭环形成”等较难用单词匹配覆盖的元叙述（Meta-narratives），写入 Judge LLM 的 `Purity Rubric` 指导原则。
   - 利用 Judge LLM 现有的打分机制，对包含软性语义泄漏的文本判定为 Purity 不达标，打回或改写，从而在不增加本地调用负担的前提下，实现语义级提纯。

## 6. Reference-Guided Judge (基于信源引导的裁判机制)

### 问题

在现有提纯管线中，Judge LLM 评估提纯后的 `think` 质量时，容易产生“幻觉/事实外推”的误判（False Positives）。
这是因为：当 Purifier 在提纯 `think` 时，根据 `refs` / 事实包补充了**准确且必要的医学专业细节**（例如某种药物的特定基因型适应症、具体临床不良反应比例等），这些细节在原始的 draft `raw_think` 中可能并不存在。如果 Judge LLM 在评估时只对比 `raw_think` 和提纯后的 `think`，或者仅凭主观常识判断，就会误认为 Purifier 进行了“无根据的外推”或“幻觉捏造”，从而打出低分或触发不必要的退回/回滚。

### 治理原则

Judge 评估必须有确凿的事实依据（Grounding）。判定“外推/幻觉”不能只凭 draft `raw_think` 的内容，而应以**输入给 Purifier 的 raw `refs` / 事实锚点**作为最高真实性标准（Ground Truth）。

### 建议方案

1. **输入增强（Grounding Context）**：
   In Judge LLM 的 Evaluation Prompt 中，除了提供提纯前的 `raw_think` 和提纯后的 `think`，必须**显式传入原始的 `refs` / 科学事实包（Confirmed Clinical & Literature Facts）**。

2. **三方比对 Rubric（三方裁判细则）**：
   细化 Judge 对“幻觉”与“合理提纯/知识对齐”的定义：
   - **合法补充（Knowledge Alignment）**：如果提纯后的 `think` 中新增了 `raw_think` 里没有的内容，但该内容**能够被传入的 `refs` / 事实包完全支撑**，则判定为“合法的知识补充与对齐”，**禁止**判定为外推或幻觉。
   - **事实外推（Over-extrapolation）/ 幻觉（Hallucination）**：只有当提纯后的新增内容既不存在于 `raw_think`，也**无法被**传入的 `refs` / 事实包支撑时，才判定为事实外推或幻觉。

3. **结构化判词与出处溯源（Traceable Judgment）**：
   Judge LLM 在输出打分和判词时，必须使用结构化 JSON 或 XML 标签，说明判定理由：
   - `added_facts`: 识别提纯后相比 draft 新增的具体医学事实（非格式调整，而是信息增量）。
   - `fact_supported`: 新增事实是否能被 `refs` 支撑？必须指出在 `refs` 中对应的段落、条目 ID 或原文。
   - `judgment`: 判定为 `valid_supplement`（合法补充） 还是 `hallucination`（幻觉）。

## 7. 外部文献 API 限流防御、学术对齐与自愈 (External API Throttling, Academic Alignment & Auto-Healing)

### 问题
在高频并发调用 PubMed API 进行文献检索时，极易触发 NCBI 官方的 **HTTP 429 (Too Many Requests)** 报错限制，若无 API Key 时默认限制为 3 rps。没有合理的限流避让自愈机制，将导致整个 RAG 检索管线因请求熔断而获取不到数据。
此外，当直接使用包含中文的实体词（如“有机阴离子转运体（hOAT家族）”）或纯中文（如“布洛芬”）直接调用 PubMed 时，由于 PubMed 仅支持英文索引，解析器会过滤中文或返回空值，进而可能通过匹配残留的英文字符片段（如“hOAT”）错误关联到无关论文（如作者为 "Hoat DM" 的材料物理论文或 "puhoatensis" 蜥蜴新种论文），引发严重的检索漂移 Bug。

### 治理原则
引入客户端硬性控频与 429 报错避让重试自愈机制，辅以中文检索实体的中英文标准医学术语翻译与学术对齐。

### 建议方案
1. **环境变量 Key 绑定**：在 `.env` 中配置 `PUBMED_API_KEY=81ec27eefbffe61380b13b5c6a26e545cf09`，将官方限流值从 3 rps 物理提高到 10 rps；并在 `.env` 中硬限频 `PUBMED_RATE_LIMIT=10`。
2. **令牌桶客户端控频限流**：使用基于 asyncio 的令牌桶算法限流器 `AsyncRateLimiter` 动态生成令牌，对 NCBI 的所有搜索和摘要请求进行硬性调度，确保不超过每秒 10 次。
3. **429 指数退避与 Retry-After 自愈**：捕捉 HTTP 429 异常。若 Header 中包含 `Retry-After` 则严格按照其指定秒数挂起协程进行避让；若没有则执行指数退避延迟（1s, 2s, 4s），进行 3 次自愈重试，最大程度避免请求失败崩溃。
4. **双通道中英翻译学术对齐**：
   - **本地对照词表**：对高频核心词建立静态中英映射字典，直接映射，零延迟且零成本。
   - **LLM 医疗术语翻译路由器**：对词表未命中的新词，调用轻量大模型翻译，限定仅输出标准英文医学通用名、MeSH 词或基因/转运体缩写符号（如将“螺旋藻胶囊”对齐为“Spirulina capsule”），从源头阻断因字符泄漏带来的检索漂移。

## 8. 推荐落地顺序

### 第一阶段：止血（极轻量本地拦截）

1. **Structure Gate** 去掉方括号硬性拦截，避免误杀正常医学表达。
2. **Leakage Scanner** 扩展为 think、answer_body、summary 全字段扫描。
3. 禁词表版本化，并在本地实现智能客套话前置切除与中性替换。

### 第二阶段：事实边界与本地对撞

1. 建立 **FactPack Builder**，物理分离 CleanedFact 与 ProvenanceMap，阻断 RAG Source 泄露。
2. 部署 **CPU 级确定性前置事实碰撞**，提取生成内容中的药物实体与数值，在本地对 refs 进行秒级碰撞，直接拦截低级幻觉以降低 API 开销。

### 第三阶段：带反馈自愈与局部事务管理

1. 重构重试机制，提取校验/Judge 失败原因作为 **Diagnostic Feedback** 定向注入重试 Prompt，实现有向自愈。
2. 将整行一票否决升级为局部切面事务管理（`partial_success`），固化成功结果，隔离失败切面。

### 第四阶段：循证裁判与 7-Metrics 打分系统

1. 部署 **Reference-Guided Judge (基于信源引导的裁判机制)**，在 Judge 输入中增加 `CleanedFact` 事实包，打消合法知识补充导致的幻觉误判。
2. 重构 Judge 评估细则，正式对齐 **Success** (格式)、**Recall** (查全率/拒答控制)、**Precision** (查准率/推理精细度)、**Faithfulness** (事实忠实度/Grounding)、**Relevance** (相关性), **Professionalism** (专业度), **Interpretability** (可解释性) 七维度打分体系。

### 第五阶段：智能路由与语义缓存层

1. 引入复杂度意图路由机制，对于简单事实查询自动降级为单切面规划，分流指派给 Lightweight 模型，对于复杂机制题才启用 8 切面并发与 Premium 模型。
2. 构建 FAISS 优秀范式缓存库与 Negative Prompts 黑名单机制，实现模型越生越稳定。

### 第六阶段：外部文献 API 限流、对齐与 429 自愈

1. 配置 `.env` 中的 `PUBMED_API_KEY` 与 `PUBMED_RATE_LIMIT=10`。
2. 实现 `AsyncRateLimiter` 异步限流器锁止与 `fetch_url_with_retry` 的 `Retry-After` 指数退避自愈，拦截 429 并避让重试。
3. 部署“本地中英对照表 + LLM 医疗翻译路由器”双通道翻译对齐机制，切断由于中文实体直接检索导致的匹配漂移 Bug，稳定 Tier 2 的文献检索获取源。

## 9. 验收标准

治理后应满足：

1. 生成模型 prompt 中不出现 `refs`、`实体库`、`图谱关系`、`在线公开检索系统抓取异常` 等工程来源词。
2. 输出的 `think`、`answer_body`、`summary` 中不出现任何工程来源与软性检索过程残留。
3. 简单事实题的答案宽度不超过问题宽度。
4. 单 planner 失败不再默认导致整行回滚，审计报告能精确体现 `partial_success` 及各 planner 状态。
5. 每条医学事实都能追溯到内部 `fact_xxx -> source` 映射。
6. 低证据样本不再触发复杂机制脑补。
7. 审计报告能区分历史原始行号与当前数据行号，避免行号漂移误读。
8. 本地 Validator 无新增 LLM 调用延迟，依靠 Trie/AC 等算法秒级完成匹配。
9. Judge LLM 对 Purifier 合理引入 `refs` 医学事实的幻觉误判率（False Positive Rate）降至接近于0。
